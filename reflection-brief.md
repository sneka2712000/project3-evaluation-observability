### 2a. Two guarantees

The discrepancy run extracted:

- stated monthly total: 10892.17
- calculated total: 9642.17
- consistent: false
- delta: -1250.0

Schema/tool validation and arithmetic validation provide different guarantees. Schema enforcement can catch malformed structure or incorrect data types, but it cannot determine whether valid numeric fields are mathematically consistent. Arithmetic validation can catch an incorrect sum, but it cannot by itself guarantee valid structured JSON.

Evidence: 02-mortgage-extraction/discrepancy-run.txt.

### 2b. Refusing to fabricate

The missing-field extraction returned:

bonus_monthly = null

Other unavailable fields were also represented as null.

The schema allows nullable values, so the extractor can represent missing evidence instead of inventing a value. This preserves the distinction between an unknown field and a known value.

Evidence: 02-mortgage-extraction/extract-run.txt.

### 2c. Normalization

The extraction system normalizes source values into structured numeric fields. For example, a source measurement such as 2,400 sq ft can be represented as numeric 2400.

Normalizing during extraction gives downstream validation and consumers a consistent data type instead of requiring every later stage to parse document-specific formatting.

Evidence: mortgage extraction tests and document fixtures.

### 3b. Source goes dark

The timeout run reports:

It later marks:

late_shipment_count

missing source: timeout reading logistics

A timeout means the source could not be read. That is different from a source being successfully read but having nothing to report.

The investigation still finishes because the failure is preserved as provenance and the coordinator continues with the sources that remain available.

Evidence: 03-supply-chain/timeout-run.txt.

### 3c. Dates as a guardrail

The briefing gives the conflicting on_time_delivery_rate values with different dates:

- 95.0 percent — supplier_audit — 2026-04-10
- 78.0 percent — logistics — 2026-04-05

Including dates prevents the two observations from automatically being interpreted as measurements taken at exactly the same time. A difference can be associated with different observation dates as well as a source disagreement.

## 4. Synthesis

### 4a. One principle

The clearest example was System 2 in discrepancy-run.txt.

The extraction produced valid structured numeric fields, but the independent validator calculated 9642.17 while the stated total was 10892.17. The system therefore flagged a -1250.0 discrepancy instead of accepting the structured extraction without verification.

This demonstrates the principle of evaluating the output rather than trusting a model-produced value automatically.

Evidence: 02-mortgage-extraction/discrepancy-run.txt.

### 4b. Confidence ≠ correctness

System 1 provides a clear calibration example.

The umbrella × exclusions slice had confidence 0.93 but accuracy 0.00, with Brier score 0.865.

This shows why confidence needs to be evaluated against observed outcomes and sliced by meaningful dimensions. A high confidence value does not itself establish correctness.

Evidence: 01-policy-pipeline/calibration-report.txt.

### 4c. Apply it

For a workflow where an LLM extracts structured results from messy input, I would combine schema validation, independent checks, controlled escalation, and provenance preservation.

Schema validation should catch malformed outputs. Independent validation should catch logical or arithmetic inconsistencies. Validated retry with escalation should handle cases where required evidence is missing or a retry is futile. For multi-source workflows, provenance-preserving conflict annotation should retain conflicting observations instead of silently choosing one source.

I would instrument:

- validation failures and discrepancy counts
- retry counts and escalation reasons
- confidence versus observed accuracy by field and document type
- source availability and timeout rates
- conflicting values with source and observation date
- missing versus unavailable source states

These signals make failures observable instead of allowing them to disappear inside an apparently successful LLM response.
